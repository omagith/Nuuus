# «Полная запись»: энергопотребление в фоне 60–120 мин (анализ, без изменений кода)

Ноутбук: Ryzen 7 6800HS, RTX 3050 Laptop 4 GB (Optimus, iGPU AMD), 16 GB RAM.
Замеры 2026-10-07, на сети. Скрипты: `research/energy_bench.py` (фейковый захват
проигрывает реальный WAV через настоящий `SharedAudioCapture` в реальном темпе),
`research/energy_ui.py` (настоящий MainWindow), `research/ctx_probe.py`. Время этапов
обработки взято из `data/logs/app.log` (реальные прогоны сегодня).
Текущие настройки пользователя: denoise=True, dereverb=True, LLM ultra (gemma4 12B),
GPU, «Трансляция» вкл.

## 1. Что измерено

| Сценарий, 60 с | CPU процесса | Прочее |
|---|---|---|
| Только индикатор уровня (поток микрофона открыт) | 0.006 ядра | — |
| Запись в WAV (+ индикатор) | **0.016 ядра** | 93.7 write-вызовов/с (3 на блок 32 мс: данные + 2 патча заголовка от `wave`), 31.5 КБ/с = 115 МБ/ч, WS 75 МБ стабильно |
| Запись + «Трансляция» на GPU (CTC light) | **0.22 ядра** | 63 вызова STT/мин (**56 partial + 7 final**), занятость STT 12 %, GPU util 4.8 %, **GPU 7.9 Вт** в среднем (пики 12.5) против 3.65 Вт простоя → **+4.3 Вт**; WS 2.0–2.4 ГБ |
| Запись + «Трансляция» на CPU | **1.51 ядра** | занятость STT 32 %, WS 1.9–2.0 ГБ |
| Окно приложения в простое, вкладка «Полная запись» | 0.031 ядра | 10.5 сигналов уровня/с |
| То же, окно **свёрнуто** | 0.023 ядра | **10.4 сигнала/с: индикатор работает и в свёрнутом окне** |

Другие факты:
- **CUDA-контекст не освобождается.** После первого тензора процесс держит 73 МБ VRAM. После `del` и `empty_cache` остаётся 72.7 МБ, до выхода из процесса. Пока жив контекст, dGPU не может уйти в D3cold и сидит в P8 на 3.3–3.5 Вт (замерено). Проверка `describe_gpu()` без тензоров даёт только 0.02 МБ.
- **keep_alive 30m.** gemma4 (3.19 ГБ VRAM) висела ровно 30 мин после последнего чанка (истекает в 14:44:39, чанк закончился в 14:14:39). Её llama-server держит 11.2 ГБ закоммиченной памяти. Параллельно висела GigaChat «Потока»: ещё 7.3 ГБ.
- **Этапы обработки, лекция 32.6 мин, GPU, текущие настройки: 15.4 мин всего.**

  | Этап | Время | Детали |
  |---|---|---|
  | Предобработка | 146 с | из них WPE на CPU 91 с, DeepFilterNet ≈ 50 с |
  | Диаризация pyannote | 151 с | RTF 0.077 |
  | Транскрипция RNN-T | 29.5 с | |
  | Структурирование gemma | **594 с** | 3 чанка: 332, 136 и 123 с |
  | Экспорт | 2.5 с | |

- **Конкуренция с «Потоком».** Лекция 20.7 мин обрабатывалась при включённом прослушивании «Потока». Диаризация шла 365.8 с (RTF 0.29, в 3.8 раза медленнее). «Поток» дважды выбросил фразы: «STT worker is behind… dropped the oldest utterance».
- **Сон на батарее.** Измерено: STANDBYIDLE на батарее = 600 с, на сети — никогда. Система с Modern Standby (S0). В коде нет ни `PowerSetRequest`, ни `SetThreadExecutionState`.
- **Обработка запускается сразу после остановки записи** (`_on_recording_saved` → `enqueue`), в том числе на батарее.

## 2. Оценка энергии на лекцию 90 мин

Мощности — типичные для 6800HS + RTX 3050 Laptop. Это оценки, не замеры.

| Что | Время | Энергия |
|---|---|---|
| Запись, «Трансляция» выкл. | 90 мин | **≈ 0.2–0.5 Вт·ч** (сверх фона системы) |
| «Трансляция» на GPU | 90 мин | ≈ +7–8 Вт·ч |
| «Трансляция» на CPU | 90 мин | ≈ +9–13 Вт·ч |
| dGPU не спит из-за висящего контекста или модели | за каждый час | ≈ +3.5 Вт·ч |
| Предобработка: WPE + DFN | ≈ 6.5 мин | ≈ 4 Вт·ч |
| Диаризация pyannote на GPU | ≈ 7 мин (≈ 25 мин при работающем «Потоке») | ≈ 5 Вт·ч (≈ 15+) |
| Транскрипция | ≈ 1.5 мин | ≈ 1 Вт·ч |
| Структурирование gemma 12B ultra: 18 слоёв на GPU + 5.8 ядра | ≈ 20–25 мин | **≈ 17–25 Вт·ч** |
| То же на light (qwen3 4B, 100 % GPU, 1 ядро) | ≈ 2–4 мин | ≈ 2 Вт·ч |
| Модель висит после обработки (keep_alive 30m) | 30 мин | ≈ 1.7 Вт·ч + 11 ГБ commit |

**Итог.** Обработка 90-минутной лекции с текущими настройками займёт ≈ 35–40 мин при 50–60 Вт. Это ≈ 30–40 Вт·ч, то есть половина или вся батарея (обычно 56–76 Вт·ч). Сама запись почти бесплатна. Основные расходы:
- LLM ultra — около 60 %;
- предобработка и диаризация — около 25 %;
- «Трансляция» — 7–13 Вт·ч за 90 мин записи.

## 3. Идеи по приоритету (эффект / стоимость)

**P0 — без этого фон дольше часа ненадёжен**
1. **Не давать системе уснуть во время записи и обработки.**
   - Как: `PowerCreateRequest` + `PowerSetRequest(PowerRequestSystemRequired)`; для обработки дополнительно `ExecutionRequired`. `DisplayRequired` не ставить: экран пусть гаснет, это −3–6 Вт.
   - Почему: на батарее система уснёт через 10 мин без ввода, и Modern Standby приостановит десктоп-приложение. Будет разрыв записи или зависшая обработка.
   - В UI предупредить: «не закрывайте крышку» (по умолчанию закрытие = сон).
   - Стоимость: XS (около 30 строк ctypes). Эффект: критичный.

**P1 — крупные рычаги**
2. **Режим с учётом батареи.**
   - Источник: `GetSystemPowerStatus` (`ACLineStatus`, `SystemStatusFlag`=энергосбережение) и `WM_POWERBROADCAST`/`PBT_APMPOWERSTATUSCHANGE` через `QAbstractNativeEventFilter`. Опционально `PowerRegisterForEffectivePowerModeNotifications` — следовать ползунку режима Windows.
   - На батарее: очередь обработки **ждёт зарядки** (статус «Ждёт зарядки», кнопка «Обработать сейчас»). Перед стартом показывать оценку «≈ 35 мин, ≈ ½ батареи».
   - Эффект: 10–40 Вт·ч с батареи на лекцию. Стоимость: S–M.
3. **Эко-профиль обработки** (на батарее по умолчанию, на сети по выбору):
   - LLM light вместо ultra: структурирование в 8–10 раз дешевле по энергии. Частичная выгрузка 12B (GPU + 6 ядер, упор в память) — худший случай для батареи.
   - denoise/dereverb выключить, либо «авто» по оценке SNR из VAD (речь против пауз).
   - Диаризация «только VAD».
   - Стоимость: S (отображение настроек).
4. **Выгружать модели сразу после работы.**
   - Lecture-LLM: `keep_alive:"0"` на последнем чанке или явная выгрузка в конце. Не делать этого, если ту же модель использует «Поток».
   - Эффект: −1.7 Вт·ч и −11 ГБ commit на лекцию, dGPU может уснуть. Стоимость: XS.
5. **Экономная «Трансляция».** Partial-вызовы — 89 % вызовов STT и около 86 % обработанного аудио: окно 6 с каждую секунду.
   - a) **Окно свёрнуто или вкладка скрыта → partial-вызовов нет.** Только final, или монитор на паузе, текст дорисовать при показе. Почти весь фоновый час окно свёрнуто, так что это ≈ −85–100 % затрат на «Трансляцию».
   - b) Режим «только готовые фразы» на батарее: ≈ −85 % STT, CPU-вариант ≈ 0.25 ядра вместо 1.5.
   - c) На батарее CPU + ONNX int8 CTC, чтобы dGPU не просыпался. У GigaAM есть `to_onnx`, onnxruntime установлен. Ожидаемо в 2–3 раза дешевле torch на CPU; нужна проверка текста.
   - d) Опция «Трансляция по умолчанию выкл. на батарее».
   - Стоимость: S (a, b, d), M (c).
6. **Обработка в отдельном процессе.**
   - Как: тот же exe с флагом `--process <wav>` через QProcess; прогресс — JSON-строками в stdout, отмена через stdin или terminate. Процесс получает `BELOW_NORMAL_PRIORITY_CLASS` + EcoQoS (`SetProcessInformation(ProcessPowerThrottling, EXECUTION_SPEED)`). Это покрывает и потоки BLAS/OpenMP, которых пер-поточный `SetThreadInformation` не достаёт.
   - Почему: при выходе процесса освобождаются CUDA-контекст (dGPU может выключиться, −3.5 Вт до конца сессии) и вся RAM: аллокаторы torch и numpy её не возвращают. Плюс изоляция падений и GUI без подлагиваний.
   - EcoQoS на CPU-этапах (WPE, CPU-часть LLM): по оценке −20–40 % энергии при +30–80 % времени.
   - Стоимость: M.
   - 6b. С встроенной Ollama (раунд 2) мы владеем деревом процессов. На время структурирования лекции можно ставить llama-server в BELOW_NORMAL + EcoQoS или в Job object с `CPU_RATE_CONTROL` (тихий режим, меньше шума вентиляторов). PID раннера находится по командной строке через Win32_Process. Только когда «Поток» не слушает. Стоимость: M.
7. **Не запускать GPU-этапы лекции параллельно с прослушиванием «Потока».**
   - Почему: замерено замедление диаризации в 3.8 раза и потерянные фразы «Потока». Работа идёт дольше при той же мощности — энергия тратится впустую.
   - Как: на время прослушивания ставить очередь на паузу, или выполнять только CPU-этапы с EcoQoS.
   - Стоимость: S.

**P2 — средние**
8. **Не держать микрофон открытым без надобности.**
   - Сейчас индикатор уровня подписан всегда. Значит, поток PortAudio открыт весь сеанс: 31 обратный вызов/с, работает audiodg, горит индикатор микрофона Windows.
   - Отписывать индикатор, когда окно свёрнуто или индикатор скрыт кнопкой «глаз» (раунд 2). Поток закроется сам, если ничего не пишется и не слушается.
   - Стоимость: S.
9. **Пауза UI-работы в свёрнутом окне.**
   - Что: сигналы уровня, перерисовка `QTextDocument` «Трансляции» на каждый partial, секундный `_tick`, опрос Ollama раз в 15 с (240 HTTP-запросов/ч).
   - Как: `changeEvent(WindowStateChange)` / `QWindow.visibility`; при восстановлении — один пересчёт.
   - Стоимость: S. Эффект малый (1–3 % ядра), но свёрнутое приложение станет почти нулевым.
10. **Контрольные точки и продолжение обработки.**
    - Кэшировать по чанкам заметки LLM: chunk-hash + модель + options. Это 60 % времени, ≈ 130 с на чанк у gemma.
    - Переиспользовать уже записываемый `clean.wav` и сохранять `turns.json` после диаризации.
    - При старте приложения предлагать продолжить незавершённую очередь.
    - Тогда сон, закрытая крышка или выход не сжигают 20–40 мин уже сделанных вычислений.
    - Стоимость: M.
11. **Удешевить предобработку.**
    - WPE: `iterations` 3→1, complex64 вместо float64 — по оценке в 2–4 раза быстрее.
    - Сначала A/B на одной записи: дают ли DFN/WPE выигрыш точности GigaAM. Шумодав часто не помогает устойчивому ASR или вредит ему.
    - Стоимость: S + A/B.
12. **Переиспользовать то, что уже посчитано при записи.**
    - Карта речи Silero из живого монитора: 1 байт на 32 мс ≈ 170 КБ на 90 мин. С ней VAD-фолбэк диаризации не нужно считать заново.
    - Final-фразы «Трансляции» сохранять как черновую расшифровку. Она доступна сразу, даже если обработка отложена до зарядки.
    - Стоимость: M.
13. **Инкрементальная предобработка во время записи.**
    - Чанки WPE (30 с) и DFN (60 с) независимы. Пачка раз в 5 мин в фоновом EcoQoS-процессе убирает ≈ 6.5 мин ожидания в конце.
    - Энергия примерно та же: только перенос нагрузки, плюс работа на эффективных частотах. Поэтому только на сети или по выбору.
    - Транскрипцию и LLM во время записи не переносить: выигрыш мал, а мешает «Потоку».
    - Стоимость: M.

**P3 — мелкие**
14. **WAV-писатель.** Буфер ≈ 1 с, патч заголовка раз в 5–10 с вместо `wave` на каждый блок. Сейчас 94 write-вызова/с, будет ~1–2/с; при падении теряется ≤ 1 с. Эффект ≈ 0.5–1 % ядра. Стоимость: XS.
15. **Пакетная доставка блоков подписчикам.** Сейчас каждый поток подписчика просыпается 31 раз/с, всего ~125 пробуждений/с. Для рекордера и индикатора — пробуждение раз в N блоков (~4/с). Эффект: глубже C-состояния, доли ватта. Стоимость: S.
16. **Silero VAD в живом мониторе → ONNX Runtime в 1 поток.** Сейчас 0.65 мс на кадр, ≈ 2 % ядра. Стоимость: S.
17. **Не держать массивы целиком.** 90 мин = 346 МБ float32 на копию. Пик 1.5–2.5 ГБ на 120 мин — RAM, не энергия. Важно, когда параллельно резидентна gemma (10 ГБ): иначе подкачка.
    - Чтение чанками: memmap int16 для предобработки и транскрипции.
    - pyannote — по пути к файлу.
    - Стоимость: M.
18. **Сжатие записи.** FLAC даёт −50 % места, Opus 32 кбит/с — −90 %. На энергию не влияет: 2 ч WAV = 230 МБ. Сжимать после обработки, во время записи оставить WAV ради устойчивости к падениям. Стоимость: S.
19. **Проверка GPU при старте без импорта torch** (nvidia-smi или DXGI). Экономит секунды CPU и около 300 МБ RAM при запуске, и GUI-процесс не открывает dGPU. Стоимость: S.
20. **`num_thread` 6→4 для LLM лекции на батарее.** CPU-слои упираются в память. По оценке −10–20 % мощности CPU при ≤ 5 % потери скорости; нужен бенч. Стоимость: XS + бенч.

**Быстрые победы (XS–S):** 1, 4, 5a, 7, 8, 9, 14. Вместе: фон с «Трансляцией» в свёрнутом окне снижается с ≈ 5 Вт до ≈ 0.3 Вт, система не засыпает, dGPU и RAM освобождаются после обработки.

## 4. Открытые проблемы (найдены попутно)
- **Ошибка: DeepFilterNet на `lecture.device=cpu` всегда падает.** Сообщение: «'NoneType' object has no attribute 'has_section'» (log 11:26:23 и 11:50:20). Причина: `_set_df_device("cpu")` вызывается до `init_df`, а конфиг df ещё не загружен (`app/lecture/preprocessing.py:320–337`). Шумоподавление молча пропускается. Владелец — CORE.
- Не проверено, засыпает ли dGPU, если процесс только открыл адаптер (`describe_gpu`), но не создал контекст. Нужен иконка-индикатор NVIDIA «GPU activity» или A/B по `BatteryStatus.DischargeRate` на батарее.
- Не проверено, создаёт ли открытый поток захвата сам power request (`powercfg /requests` требует прав администратора). Пункт 1 нужен в любом случае.
- GPU-замеры частично зашумлены: на той же карте одновременно работали другие процессы. Цифры чистого прогона: 7.9 Вт против 3.65 Вт простоя.
